# 演员合集与插件存储库设计

- 日期：2026-11-03
- 仓库：DenzelVincent/jellyfin-plugin-metatube（fork 自 metatube-community/jellyfin-plugin-metatube），分支 main，代码基线 `a65ef74`
- 状态：设计已确认；2026-11-03 追加的演员合集最小片数阈值、系列合集名翻译（D12–D14）、分发指向隔离（D15）已并入第 4/6/8 节，V1/V3/V7 编译实测回填第 9 节
- 目标运行时：Jellyfin 12.4（用户实测当前 10.11 构建可正常加载与刮削）

## 1. 目标

1. 新增「按演员自动创建合集」能力：每位演员一个合集，一部影片可同时归属多个演员合集，由独立开关控制，并可用最小片数阈值过滤（默认 3）。
2. 合集封面自动取该演员在 MetaTube 的照片。
3. 系列合集名可翻译：现有系列名多为日文，不利于阅读，翻译结果持久化成对照表，保证同一系列永远同名。
4. 把插件配置页面（以及插件在 Jellyfin UI 里露出的其余英文文案）全部中文化。
5. 为这个 fork 建立独立可用的 Jellyfin 插件存储库，使新构建能被服务端发现并安装。
6. 分发指向彻底与本仓库解耦：构建产物、Release、`dist` 分支、程序集元数据里的仓库地址全部落在自己的仓库，不再指向上游。
7. 为后续 Jellyfin 大版本升级保留一条提前发现破坏点的机制。

## 2. 已确认决策

| # | 决策项 | 结论 | 依据/理由 |
| --- | --- | --- | --- |
| D1 | 合集语义 | 一人一合集，影片可同时属于多个演员合集 | 用户选定 |

## 4. 合集能力设计（演员合集 + 系列合集名翻译）

### 4.1 组件与职责

| 单元 | 职责 | 如何使用 | 依赖 |
| --- | --- | --- | --- |
| `PluginConfiguration.EnableActorCollections`（新） | 演员合集开关，默认 `false` | 任务开头门控 | 无 |
| `PluginConfiguration.ActorCollectionMinMovieCount`（新，int，默认 3） | 最小片数阈值：**只门控创建**；`<1` 按 1 处理并记 `Warn` | 任务在「是否新建」这一步读取 | 无 |
| `ScheduledTasks/SyncActorCollectionsTask.cs`（新，整文件 `#if !__EMBY__`） | 唯一的合集写入者：扫描 → 归集 → 差异对齐 | Jellyfin 计划任务页，自动触发或手动运行 | `ILibraryManager`、`ActorCollectionSync` |
| `Helpers/ActorCollectionSync.cs`（新） | 纯计算：把影片列表折算成「演员键 → (显示名, pid, 影片id集合)」，并算出与现有合集的成员差集 | 由任务调用；不触碰服务端 API | `ProviderId`、`Extensions` |
| `Extensions/JellyfinExtensions.cs`（`#region Collection` 追加） | 服务端 API 薄封装：按 pid/名字查合集、建合集、增删成员、写 pid | 只被任务调用 | `ILibraryManager` |
| `Providers/CollectionImageProvider.cs`（新，整文件 `#if !__EMBY__`） | 让带 MetaTube pid 的合集可从 MetaTube 取演员照片作为 Primary 远程图 | Jellyfin 图片框架自动发现 | `ApiClient`，形状照 `ActorImageProvider` |

拆出 `ActorCollectionSync` 的原因：折算与差集计算是纯函数，可独立读懂、可在无服务端环境下自测；服务端 API 的不确定性全部集中在 `Extensions` 与任务两个文件里，一旦 12.x 接口变化，改动面最小。

### 4.2 数据流

1. 门控：开关关闭 → 记录一条 `Info` 日志并结束（不上报失败）。
2. 查询：沿用 `OrganizeMetadataTask.cs:69-79` 的查询条件（`MediaType.Video` + `Movie` + `HasAnyProviderId = MetaTube`）。
3. 折算：逐条影片取 `People` 中 `PersonKind.Actor` 的人员，构造 `演员键 → (显示名, 源, 演员ID, {影片id})`。
   - 演员键优先取人员身上的 `MetaTube` pid（`源,ID`）；解析不到时退回演员名（大小写折叠）。pid 缺失只影响改名跟踪与封面，不影响归属。
4. 对齐：对每位演员
   - **先过创建门槛**：查不到现有合集且期望成员数 `< ActorCollectionMinMovieCount` → 跳过这位演员（记 `Debug`，说明当前片数与阈值），不建合集；查到了现有合集则**不论片数继续对齐**（D12：阈值只门控创建）；
   - 先按合集 pid 查现有合集；查不到再按同名 `BoxSet` 查；都查不到则创建并写 pid；
   - 命中用户手建的同名合集时**复用并补写 pid**（名字一致说明意图一致），不做重命名、不另建同名合集；若因此与用户期待不符，用户可在 UI 里删掉 pid 或改名后由下一轮重新创建；
   - 取该合集当前成员 id 集合，与期望集合求差；只写差集（增、删），完全一致则不做任何写入；
   - **成员对齐的作用域只限本次扫描得到的 MetaTube 影片**：合集里非本次扫描范围的成员（手工加入的其它条目、其它来源的影片）一律不删，即使它不在期望集合里。这条是防止一次同步吃掉用户手工整理的合集的关键约束；
   - 新建合集时记录演员 pid，供 `CollectionImageProvider` 解析封面。
5. 进度与取消：按演员序号上报进度；每轮检查 `cancellationToken`。

### 4.3 幂等、清理与失败处理

- 幂等：判定标准是「合集成员集合是否等于期望集合」，与运行次数无关；重复运行不产生写库。
- 清理：演员变更（重刮削、演员替换表、真实演员名开关）导致的失配成员，在同一次对齐中被移除；移除范围同样只限本次扫描得到的 MetaTube 影片，用户手工塞进合集的其它条目不动。
- 开关关闭后**不删除**已生成的合集。删除合集是不可逆动作，误删代价远大于留下空壳；需要清理时由用户在 UI 手动删除，README 写明。
- 阈值调高**不回收**已有合集（D12），只影响后续新建；阈值调低会让下一轮扫描集中新建一批合集，与首轮同理。
- 已存在的合集即使片数跌破阈值也继续对齐成员，最差情况是合集变空壳（该演员的影片全部移出库），空壳同样由用户手删。这条是「只门控创建」的直接后果，README 要写明，避免用户以为调高阈值能清理合集。
- 单个演员处理失败只记日志并继续下一位，与 `OrganizeMetadataTask.cs:116-119` 同口径；整轮不抛异常中断。
- 首轮会集中创建大量合集，属预期；进度上报 + 可随时取消。

### 4.4 平台边界

- 新开关与新任务整块 `#if !__EMBY__`，先例是 `Extensions/JellyfinExtensions.cs` 的文件级条件编译。理由：Emby 看不到一个不会生效的开关。
- CI 的 `Release.Emby` 目标（`dotnetcore.yml:46`）必须继续编译通过，且 net6.0 校验（`:52-53`）不受影响。V3 已用 .NET SDK 10.0.403 单独编过 `Release.Emby`（`0 Warning / 0 Error`），说明 B 阶段动 csproj 不会波及 Emby 目标。
- `CollectionImageProvider` 若需要同时编到 Emby，则照 `ActorImageProvider.cs:26-31` 写双签名；本轮按 D2 只做 Jellyfin 分支。
- 系列翻译是**跨平台**能力（改的是 `TranslationHelper` 与 `PluginConfiguration`，不带 `#if`），只有「引擎结果自动回写对照表」这一步门控在 `#if !__EMBY__`：Emby 的 `BasePluginSimpleUI<PluginConfiguration>` 怎么从刮削线程持久化配置没验证过，不值得为它冒险。Emby 端因此是「查表 + 调引擎，但表不自动增长」，用户需要手工维护对照表——README 写明这个差异。

### 4.5 合集命名与实现约定

- 合集名 = 演员显示名原样，不加前后缀、不做模板。名字天然跟随「真实演员名/演员替换表」的处理结果，与库内演员一致。
- 只处理 `Actor`，不处理 `Director`（导演已有独立开关，是否也建合集属后续需求）。
- 代码注释用中文，写「为什么/坑/副作用」，不写复述语句的注释。
- 日志沿用仓库既有 `Logger.Debug/Info/Warn/Error` 扩展与既有风格（带 `{0}` 占位与对象上下文），五级分明：建合集与增删成员记 `Info`，pid 缺失与同名冲突记 `Warn`，单个演员失败记 `Error`，逐条扫描细节记 `Debug`。

### 4.6 系列合集名翻译（译文对照表持久化）

**开关与存储**

| 单元 | 职责 |
| --- | --- |
| `PluginConfiguration.EnableSeriesTranslation`（新 bool，默认 `false`） | 门控整条系列翻译链路。**不**塞进 `TranslationMode` 枚举：那个枚举现在是单选下拉（`Disabled/Title/Summary/Both`），加 `Series` 位会炸出 7 种组合，且 Emby 的 `EditableOptionsBase` 怎么渲染 flags 枚举没验证过 |
| `PluginConfiguration.RawSeriesTranslationTable`（新 string，默认空）+ `GetSeriesTranslationTable()` | 每行 `原文=译文`，格式与既有三张替换表一致（`Helpers/SubstitutionTable.cs:11-30`）。配置页是可编辑文本域，用户能手工纠正误译，改完下一张影片即生效 |

**取译文的顺序**（在 `TranslationHelper.TranslateAsync` 里加一个 block，紧接 Title/Summary 之后）

1. 整键精确查表命中 → 直接用表值，**零 API 调用**；表值是空串 → 视为「这个系列就要保留原文」的显式意图，同样不调引擎。
2. 未命中且 `ShouldSkipTranslation` 判定已含中文 → 原样返回。
3. 未命中 → 调引擎，复用 `TranslateFieldSafeAsync`（失败自动保留原文，`:86-100`）。
4. 引擎成功 → 写进进程内 `ConcurrentDictionary`，并追加一行到对照表后调 `Plugin.Instance.UpdateConfiguration(...)` 持久化。写回只在 `#if !__EMBY__` 分支做（见 4.4）。

**为什么必须是持久表而不是内存缓存**：合集靠 `CollectionName` **按名字匹配**，同一个系列两次刮削拿到不同译文，库里就会裂成两个合集。内存缓存挡得住一次扫描内的重复，挡不住重启后引擎换译法；持久表把这条路堵死，顺带给了「引擎译错我就改一行」的出口。

**两条硬约束**
- 禁止调用 `SubstitutionTable.Substitute(string)`（`:42-49`）：它对每个键做**子串**替换，系列名之间存在前缀包含时会误伤。本表只允许 `TryGetValue` 整键匹配。
- 缓存重建靠「当前 raw 串 ≠ 建表时的 raw 串」判断，在锁内重建。这样一个 `ConcurrentDictionary` 同时覆盖用户在配置页的编辑与自动回写，不必每张影片重解析文本。

**副作用与迁移代价（写进 README）**
- 开启后**已刮过的影片不会自动改名**：合集名在刮削时写入（`MovieProvider.cs:176-181`），必须全库重刮/覆盖刷新元数据才生效。
- 旧的日文合集不会被自动删除或合并，需手动清理，残留行为列 V9。
- 系列标签（`:187-189`）与 `{series}` 模板变量（`:129`）跟着一起变译文——这是 D13 的自觉后果，不是 bug。
- 元数据语言混用会裂合集：目标语言不同（`zh-CN` / `zh-TW`）会各自译一遍，`ja` 目标则在 `TranslationHelper.cs:32-33` 直接抛异常、该影片保留原文。列 V10，README 建议库内统一元数据语言。

## 5. Jellyfin 12.x 适配设计

1. `csproj`：Jellyfin 配置的目标框架 `net9.0` → `net10.0`；`Jellyfin.Controller`/`Jellyfin.Model` `10.11.0` → `12.0.0`（D7）。
2. SDK 版本属性化：包版本改为 `$(JellyfinSdkVersion)`，`<PropertyGroup>` 给默认值 `12.0.0`，便于第 4 点的预览编译在不改代码的前提下换版本试编。
3. `dotnetcore.yml`：`setup-dotnet` 增加 `10.0.x`，保留 `6.0.x`（Emby 目标要求，理由见 `csproj:24-29` 注释）。
4. 预览编译工作流（新增，不发布产物）：`workflow_dispatch` 输入 `JellyfinSdkVersion`（默认 `12.4.0`），只做 `dotnet build --configuration Release` 并汇报错误；用于在升级 Jellyfin 大版本前发现 API 破坏点。这是目标 7 的落地机制，而不是靠运气。
5. 破坏点适配范围以实测为准，**已执行**（V3）：探针副本只改 csproj、业务代码零改动下 `Release` 与 `Release.Emby` 双目标均 `0 Error`。结论是 B 阶段的改动面只有本节第 1、2、3、4、9 步，全在 csproj 与 CI 两个文件里，不存在需要「一边猜一边改」的业务代码破坏点。
6. 编译通过不等于语义正确：V3 只证明 12.0.0 SDK 下现有调用仍能编过，12.0 重构了播放列表与合集存储这件事（见第 3 节「官方 12.0 提示…」一条）仍要靠 V4/V2 的实机运行确认。
7. 「构建留在 10.11」这条退路保留但已失去吸引力：升 SDK 的编译成本实测为零，而 catalog 的 `targetAbi` 由包版本推导（`manifest.py:40-48`），不升就发不出 `12.x` 的 ABI 声明。最终是否必须升仍由 A 阶段 V2 的「从仓库安装」实测定夺。
8. 规模分叉**已判定不触发**：V3 的错误列表为空，远低于「跨 5 个以上文件或涉及 Provider 接口整体换签名」的拆分阈值，B 不另立实现计划，仍在本设计内按 A→B→C→D→E→F 推进。
9. 新增步骤（V3 带出的唯一副作用）：Jellyfin 目标升 `net10.0` 后，`csproj:37-39` 那条无条件的 `System.Memory` 显式引用成了冗余，会多出 2 条 `NU1510` 警告。归因实测：只改 TFM → 出警告；只改包版本 → 0 警告。处理办法是直接删掉 `csproj:38` 的 `PackageReference`，已在探针上验证删除后 `Release`（net10.0 + 12.0.0）与 `Release.Emby`（net6.0）双双 `0 Warning / 0 Error`。

## 6. 插件存储库设计

### 6.1 种子 manifest

fork 的 `dist` 分支需要一份种子文件（`manifest.py:105` 会读它）：

```json
[{"guid":"01cc53ec-c415-4108-bbd4-a684a9801a32","name":"MetaTube",
  "description":"MetaTube 元数据插件（个人分支）：按系列与演员自动创建合集、中文字幕与无码破解角标、字段级聚合与翻译。",
  "overview":"Jellyfin/Emby 元数据插件，依赖 MetaTube Server 提供数据。",
  "owner":"DenzelVincent","category":"Metadata",
  "imageUrl":"https://raw.githubusercontent.com/DenzelVincent/jellyfin-plugin-metatube/main/Jellyfin.Plugin.MetaTube/thumb.png",
  "versions":[]}]
```

`description`/`overview` 就是 Jellyfin 插件列表里显示的文案，因此中文化落在这里，不在代码里（D6 的第 4 项）。

### 6.2 CI 容错改造

`manifest.py` 读种子失败（404、网络不可达）时，回退到脚本内置的同内容 skeleton，使首次发布不需要「先有 dist 才能有 dist」。同时保留现有语义：已有条目沿用旧 `checksum/timestamp`，历史缺失的 release 由 releases API 重建（`manifest.py:128-140`）。

### 6.3 发布与注册

- 发布：推代码 + 打 tag `v<version>`（`dotnetcore.yml:5-6`），CI 构建双目标、生成并强推 `dist`、发 Release 带两个 zip。fork 需确认 Actions 已启用；`permissions: contents: write` 已声明（`:12-13`）。
- 注册 URL：
  - 主：`https://raw.githubusercontent.com/DenzelVincent/jellyfin-plugin-metatube/dist/manifest.json`
  - 备（国内可达性）：`https://cdn.jsdelivr.net/gh/DenzelVincent/jellyfin-plugin-metatube@dist/manifest.json`
  - 已知残留风险：zip 仍从 `github.com/.../releases/download` 取，代理不可用时安装失败，这一点换 URL 解决不了，README 写明。
- 关键验收（也是 B 阶段规模的决定因素）：在 12.4 服务端「从仓库安装」——先装当前 `targetAbi=10.11.0.0` 的构建，观察服务端是否列出/接受它；再装升 SDK 后的构建。**只有走完这条安装路径才算存储库交付完成**，本地能加载不等于仓库可用。

### 6.4 分发指向隔离（D15）

插件身份不变（D8），但产物与元数据一律指向 `DenzelVincent/jellyfin-plugin-metatube`：

| 位置 | 现值 | 改为 |
| --- | --- | --- |
| `csproj:13` `RepositoryUrl` | 上游 `.git` | 本仓库 `.git` |
| `csproj:14` `PackageProjectUrl` | 上游 | 本仓库 |
| `csproj:15` `PackageLicenseUrl` | 上游 `blob/main/LICENSE` | 本仓库同名路径 |
| `scripts/manifest.py:16-17` 默认仓库 | 缺省回落上游 | 缺省回落本仓库（CI 里 `GITHUB_REPOSITORY` 已覆盖，只有本地跑脚本才会用到缺省值） |
| `ScheduledTasks/UpdatePluginTask.cs:69` | 上游 releases API | 本仓库 releases API（不改则 Emby 端自更新会把上游构建盖下来） |
| `README.md:4,12-28,54-61,118,122` | 上游徽章/Release/安装链接 | 徽章与安装链接改本仓库；`README.ja.md` 不动 |
| `configPage.html:16`、`:190` 的 Learn more / 模板变量文档 | 上游社区 wiki | **保留上游**：文档只有那一份，本仓库不自建 wiki；仅在 E 阶段中文化文案 |

`dist` 分支不需要预先创建：CI 的 `dotnetcore.yml:66-72` 用 `${GITHUB_REPOSITORY}` 强推 orphan 分支，首次发布即在本人仓库下生成 `dist/manifest.json`。前提是 6.2 的 404 容错先落地，否则首次 CI 在 `manifest.py:105` 就中断。

### 6.5 与上游同步时的保名清单

上面 6 处每次 merge 上游都会被改回去。做法：本节表格随设计文档留存，每次同步后按表逐条核对一遍；不在脚本里加自动断言——校验覆盖不全反而给人错误的安全感，核对清单够用。

## 8. 明确不做

- 每片最多归属数上限、演员合集名模板（演员合集固定用演员显示名，见 4.5）。
- 演员名翻译：本轮只译系列名，演员名多数本就是汉字。
- 导演合集、厂商/label 合集等其他维度的合集。
- 关闭开关时批量删除合集；阈值跌破时自动删除合集（D12 已定：阈值只门控创建）。
- 旧日文系列合集的自动改名与自动合并：开启译文后靠全库重刮 + 手删旧合集过渡。
- Emby 侧的演员合集实现，以及 Emby 端译文对照表的自动回写（见 4.4）。
- 为 fork 改插件 GUID/名字做「与上游并存的第二个插件」（D15 只换分发指向）。
