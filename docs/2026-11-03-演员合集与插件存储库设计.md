# 演员合集与插件存储库设计

- 日期：2026-11-03
- 仓库：DenzelVincent/jellyfin-plugin-metatube（fork 自 metatube-community/jellyfin-plugin-metatube），分支 main，代码基线 `a65ef74`
- 状态：设计已确认；2026-11-03 追加的阈值/系列译文对照表/分发隔离三项决策（D12–D15）与「12.x 真升挪到最后、条件触发」（D7/D10 修订）已并入正文，V1/V3/V7 编译实测见第 9 节。实现计划见 `docs/2026-11-03-演员合集与插件存储库实现计划.md`；制定计划时新发现的四处事实已回填本文——① 配置页早已有 `zhCN` 中文字典（D 阶段范围缩小）、② 演员键由「优先 pid」改为「显示名」（避免同演员裂成两个合集）、③ 10.11 的合集 API 面经反射实测（无按名查找，须自建索引）、④ 版本属性化会打断 `manifest.py` 的 `targetAbi` 推导（E 阶段连带改）。
- 目标运行时：Jellyfin 12.4（用户实测当前 10.11 构建可正常加载与刮削）

## 1. 目标

1. 新增「按演员自动创建合集」能力：每位演员一个合集，一部影片可同时归属多个演员合集，由独立开关控制，并可用最小片数阈值过滤（默认 3）。
2. 合集封面自动取该演员在 MetaTube 的照片。
3. 系列合集名可翻译：现有系列名多为日文，不利于阅读，翻译结果持久化成对照表，保证同一系列永远同名。
4. 把插件配置页面（以及插件在 Jellyfin UI 里露出的其余英文文案）全部中文化。
5. 为这个 fork 建立独立可用的 Jellyfin 插件存储库，使新构建能被服务端发现并安装。
6. 分发指向彻底与本仓库解耦：构建产物、Release、`dist` 分支、程序集元数据里的仓库地址全部落在自己的仓库，不再指向上游。
7. 为后续 Jellyfin 大版本升级保留一条提前发现破坏点的机制。

## 4. 合集能力设计（演员合集 + 系列合集名翻译）

### 4.1 组件与职责

| 单元 | 职责 | 如何使用 | 依赖 |
| --- | --- | --- | --- |
| `PluginConfiguration.EnableActorCollections`（新） | 演员合集开关，默认 `false` | 任务开头门控 | 无 |
| `PluginConfiguration.ActorCollectionMinMovieCount`（新，int，默认 3） | 最小片数阈值：**只门控创建**；`<1` 按 1 处理并记 `Warn` | 任务在「是否新建」这一步读取 | 无 |
| `ScheduledTasks/SyncActorCollectionsTask.cs`（新，整文件 `#if !__EMBY__`） | 唯一的合集写入者：扫描 → 归集 → 差异对齐 | Jellyfin 计划任务页，自动触发或手动运行 | `ILibraryManager`、`ICollectionManager`、`ActorCollectionSync` |
| `Helpers/ActorCollectionSync.cs`（新） | 纯计算：把影片列表折算成「演员键 → (显示名, pid, 影片id集合)」，并算出与现有合集的成员差集 | 由任务调用；不触碰服务端 API | 无（值类型进出） |
| `Extensions/JellyfinExtensions.cs`（`#region Collection` 追加） | 服务端 API 薄封装：读演员、建合集、增删成员、写 pid | 只被任务调用 | `ILibraryManager`、`ICollectionManager` |
| `Providers/CollectionImageProvider.cs`（新，整文件 `#if !__EMBY__`） | 让带 MetaTube pid 的合集可从 MetaTube 取演员照片作为 Primary 远程图 | Jellyfin 图片框架自动发现 | `ApiClient`，形状照 `ActorImageProvider` |

拆出 `ActorCollectionSync` 的原因：折算与差集计算是纯函数，可独立读懂、可在无服务端环境下自测；服务端 API 的不确定性全部集中在 `Extensions` 与任务两个文件里，一旦 12.x 接口变化，改动面最小。

### 4.2 数据流

1. 门控：开关关闭 → 记录一条 `Info` 日志并结束（不上报失败）。
2. 查询：沿用 `OrganizeMetadataTask.cs:69-79` 的查询条件（`MediaType.Video` + `Movie` + `HasAnyProviderId = MetaTube`）。
3. 折算：逐条影片取 `GetPeople(item)` 中 `Type == PersonKind.Actor` 的人员，构造 `演员键 → (显示名, 源, 演员ID, {影片id})`。
   - 演员键 = **演员显示名**（`Trim().ToLowerInvariant()`），pid 只作为该组的附加标识（取组内第一个非空 pid）。此处推翻原方案「键优先取 pid」：`MovieProvider.cs:319-324` 里 `actor.SetPid` 只在演员有照片时才调用，同一演员在库里完全可能一部分影片带 pid、一部分不带——按 pid 作键会把这位演员裂成两个合集，按名字作键则永远一组。
   - 显示名变化（真实演员名开关、演员替换表）时：新名字在下一轮建新合集；旧合集按名字命中后被对齐到剩余成员，失配的影片从旧合集里移除，剩下的空壳由用户手删，与 4.3「不删合集」一致。
   - 用户手改合集名造成的失配靠 pid 兜：查现有合集时**先按 pid** 命中（尊重用户改名，只对齐成员、不改名），再按名字命中（复用用户手建的同名合集并补写 pid）。
4. 对齐：对每位演员
   - **先过创建门槛**：查不到现有合集且期望成员数 `< ActorCollectionMinMovieCount` → 跳过这位演员（记 `Debug`，说明当前片数与阈值），不建合集；查到了现有合集则**不论片数继续对齐**（D12：阈值只门控创建）；
   - 先按合集 pid 查现有合集；查不到再按同名 `BoxSet` 查；都查不到则创建并写 pid；
   - 命中用户手建的同名合集时**复用并补写 pid**（名字一致说明意图一致），不做重命名、不另建同名合集；若因此与用户期待不符，用户可在 UI 里删掉 pid 或改名后由下一轮重新创建；
   - 取该合集当前成员 id 集合，与期望集合求差；只写差集（增、删），完全一致则不做任何写入；
   - **成员对齐的作用域只限本次扫描得到的 MetaTube 影片**：合集里非本次扫描范围的成员（手工加入的其它条目、其它来源的影片）一律不删，即使它不在期望集合里。这条是防止一次同步吃掉用户手工整理的合集的关键约束；
   - 新建合集时记录演员 pid，供 `CollectionImageProvider` 解析封面。
5. 进度与取消：按演员序号上报进度；每轮检查 `cancellationToken`。

### 4.3 幂等、清理与失败处理

- 幂等：判定标准是「合集成员集合是否等于期望集合」，与运行次数无关；重复运行不产生写库。
- 清理：演员变更（重刮削、演员替换表、真实演员名开关）导致的失配成员，在同一次对齐中被移除；移除范围同样只限本次扫描得到的 MetaTube 影片，用户手工塞进合集的其它条目不动。
- 开关关闭后**不删除**已生成的合集。删除合集是不可逆动作，误删代价远大于留下空壳；需要清理时由用户在 UI 手动删除，README 写明。
- 阈值调高**不回收**已有合集（D12），只影响后续新建；阈值调低会让下一轮扫描集中新建一批合集，与首轮同理。
- 已存在的合集即使片数跌破阈值也继续对齐成员，最差情况是合集变空壳（该演员的影片全部移出库），空壳同样由用户手删。这条是「只门控创建」的直接后果，README 要写明，避免用户以为调高阈值能清理合集。
- 单个演员处理失败只记日志并继续下一位，与 `OrganizeMetadataTask.cs:116-119` 同口径；整轮不抛异常中断。
- 首轮会集中创建大量合集，属预期；进度上报 + 可随时取消。

### 4.4 平台边界

- 新开关与新任务整块 `#if !__EMBY__`，先例是 `Extensions/JellyfinExtensions.cs` 的文件级条件编译。理由：Emby 看不到一个不会生效的开关。
- CI 的 `Release.Emby` 目标（`dotnetcore.yml:46`）必须继续编译通过，且 net6.0 校验（`:52-53`）不受影响。V3 已用 .NET SDK 10.0.403 单独编过 `Release.Emby`（`0 Warning / 0 Error`），说明将来 F 阶段动 csproj 不会波及 Emby 目标。
- `CollectionImageProvider` 若需要同时编到 Emby，则照 `ActorImageProvider.cs:26-31` 写双签名；本轮按 D2 只做 Jellyfin 分支。
- 系列翻译是**跨平台**能力（改的是 `TranslationHelper` 与 `PluginConfiguration`，不带 `#if`），只有「引擎结果自动回写对照表」这一步门控在 `#if !__EMBY__`：Emby 的 `BasePluginSimpleUI<PluginConfiguration>` 怎么从刮削线程持久化配置没验证过，不值得为它冒险。Emby 端因此是「查表 + 调引擎，但表不自动增长」，用户需要手工维护对照表——README 写明这个差异。

### 4.5 合集命名与实现约定

- 合集名 = 演员显示名原样，不加前后缀、不做模板。名字天然跟随「真实演员名/演员替换表」的处理结果，与库内演员一致。
- 只处理 `Actor`，不处理 `Director`（导演已有独立开关，是否也建合集属后续需求）。
- 代码注释用中文，写「为什么/坑/副作用」，不写复述语句的注释。
- 日志沿用仓库既有 `Logger.Debug/Info/Warn/Error` 扩展与既有风格（带 `{0}` 占位与对象上下文），五级分明：建合集与增删成员记 `Info`，pid 缺失与同名冲突记 `Warn`，单个演员失败记 `Error`，逐条扫描细节记 `Debug`。

### 4.6 系列合集名翻译（译文对照表持久化）

**开关与存储**

| 单元 | 职责 |
| --- | --- |
| `PluginConfiguration.EnableSeriesTranslation`（新 bool，默认 `false`） | 门控整条系列翻译链路。**不**塞进 `TranslationMode` 枚举：那个枚举现在是单选下拉（`Disabled/Title/Summary/Both`），加 `Series` 位会炸出 7 种组合，且 Emby 的 `EditableOptionsBase` 怎么渲染 flags 枚举没验证过 |
| `PluginConfiguration.RawSeriesTranslationTable`（新 string，默认空） | 每行 `原文=译文`，格式与既有三张替换表一致（`Helpers/SubstitutionTable.cs:11-30`）。配置页是可编辑文本域，用户能手工纠正误译，改完下一张影片即生效。解析不进配置类（原设计的 `GetSeriesTranslationTable()` 访问器**没做**）：整表的解析、缓存与回写都在 `Helpers/SeriesTranslationStore`，配置类只存原始串，跟 `RawFieldPriority` 一样保持零依赖 |

**取译文的顺序**（在 `TranslationHelper.TranslateAsync` 里加一个 block，紧接 Title/Summary 之后）

1. 整键精确查表命中 → 直接用表值，**零 API 调用**；表值是空串 → 视为「这个系列就要保留原文」的显式意图，同样不调引擎。
2. 未命中且 `ShouldSkipTranslation` 判定已含中文 → 原样返回。
3. 未命中 → 调引擎，复用 `TranslateFieldSafeAsync`（失败自动保留原文，`:86-100`）。
4. 引擎成功 → 追加一行到对照表后调 `Plugin.Instance.UpdateConfiguration(...)` 持久化；内存表不单独插条目，靠下一次读时「raw 串变了」在锁内整表重建。写回只在 `#if !__EMBY__` 分支做（见 4.4）。
   - **并发按「先到先得」收敛**：能走到写回说明查表时这行还不存在，此时若已存在就是同一次刷新里另一部同系列影片先写完——采用先到的译文、不覆盖。一个系列十几部影片并发走这条链路是常态，各写各的正是裂合集。`Persist` 因此返回「生效译文」而不是 `void`，入库名以返回值为准。
   - **入表的键与值先 `Trim`、含换行则整条拒收**：表是按行存的（`Parse` 逐行读、`ToString` 用 `\n` 拼），带换行会写出多余的行，下次读成一个「没有等号 = 保留原文」的键，只能手改 `config.xml` 才清得掉；不裁又会「写进去是 `B=乙`、拿 `" B "` 查永远 miss」。含换行的译文同样不拿来当合集名，直接保留原文。

**为什么必须是持久表而不是内存缓存**：合集靠 `CollectionName` **按名字匹配**，同一个系列两次刮削拿到不同译文，库里就会裂成两个合集。内存缓存挡得住一次扫描内的重复，挡不住重启后引擎换译法；持久表把这条路堵死，顺带给了「引擎译错我就改一行」的出口。

**两条硬约束**
- 禁止调用 `SubstitutionTable.Substitute(string)`（`:42-49`）：它对每个键做**子串**替换，系列名之间存在前缀包含时会误伤。本表只允许 `TryGetValue` 整键匹配。
- 缓存重建靠「当前 raw 串 ≠ 建表时的 raw 串」判断，在锁内重建。这样一个整表对象（`SubstitutionTable` 实例，非并发字典）同时覆盖用户在配置页的编辑与自动回写，不必每张影片重解析文本；读与写都在同一把锁内，重建期间不会读到半新半旧的表。

**副作用与迁移代价（写进 README）**
- 开启后**已刮过的影片不会自动改名**：合集名在刮削时写入（`MovieProvider.cs:176-181`），必须全库重刮/覆盖刷新元数据才生效。
- 旧的日文合集不会被自动删除或合并，需手动清理，残留行为列 V9。
- 系列标签（`:187-189`）与 `{series}` 模板变量（`:129`）跟着一起变译文——这是 D13 的自觉后果，不是 bug。
- 元数据语言混用会裂合集：目标语言不同（`zh-CN` / `zh-TW`）会各自译一遍，`ja` 目标则在 `TranslationHelper.cs:32-33` 直接抛异常、该影片保留原文。列 V10，README 建议库内统一元数据语言。
- **配置页保存会覆盖刮削期的自动回写**：`UpdateConfiguration` 写的是整个配置对象，页面上的「保存」提交的是打开页面那一刻的快照。首次全库重刮期间如果开着设置页，引擎这几分钟新增的译文行会被页面快照里的旧表整体盖掉——表现是「明明提示持久化了，下次还在调引擎」。锁只能保证插件进程内不互相踩，管不住这个跨来源的丢更新。README 写明：首轮重刮期间不要停留在设置页，别在刮削进行中点保存。列 V8。

## 5. Jellyfin 12.x 适配设计（拆两半：探测机制早做，真升最后做）

### 5.1 随 E 阶段做的两小步（不改变发布产物的 ABI）

### 5.3 挪到最后换来的唯一新风险（要记账，不是免费的）

## 8. 明确不做

- 每片最多归属数上限、演员合集名模板（演员合集固定用演员显示名，见 4.5）。
- 演员名翻译：本轮只译系列名，演员名多数本就是汉字。
- 导演合集、厂商/label 合集等其他维度的合集。
- 关闭开关时批量删除合集；阈值跌破时自动删除合集（D12 已定：阈值只门控创建）。
- 旧日文系列合集的自动改名与自动合并：开启译文后靠全库重刮 + 手删旧合集过渡。
- Emby 侧的演员合集实现，以及 Emby 端译文对照表的自动回写（见 4.4）。
- 为 fork 改插件 GUID/名字做「与上游并存的第二个插件」（D15 只换分发指向）。
