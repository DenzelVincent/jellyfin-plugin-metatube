# 演员艺名优选与主辅翻译引擎设计

- 日期：2026-11-14
- 状态：设计已获用户批准，待实施
- 涉及仓库：`jellyfin-plugin-metatube`（插件）、`metatube-sdk-go`（服务端）
- 取代：`2026-11-11-演员别名表与名字解析设计.md`（整体，独有内容已并入本文）；
  `2026-11-11-翻译多选与服务端术语字典设计.md` 的演员翻译与引擎选择部分（术语字典链路仍有效）
- 台账：`2026-11-03-演员合集与插件存储库实现计划.md` R27

## 1. 背景与目标

两条需求（2026-11-14 用户提出）：

1. **删除插件与服务端里翻译演员名的全部逻辑**，不再保留演员译名，只保留艺名；
   艺名在多个演员数据源返回的名字和别名中**优选汉字多的**；检查演员合集相关逻辑是否受影响。
2. **翻译引擎改为主引擎 + 辅引擎**：主引擎固定使用现有 OpenAI 兼容翻译能力
   （接口地址、密钥、模型自行填写）；辅引擎可选百度、谷歌免费两个。

用户已拍板的边界：

| 决策点 | 结论 |
|---|---|
| 主辅调用关系 | 主引擎优先；失败或未配置时回退辅引擎；辅引擎可选「无」 |
| 存量 Person / 旧译名 | 不自动归一；用户手动删旧 Person 后全量重刮 |
| 字典已有艺名 | 发现汉字严格更多的名字时自动升级；手动改过的不升级 |
| 实现结构 | 混合：汉字优选规则在服务端，引擎编排在插件 |
| 旧数据列 | `translated_name` / `translated_key` / `translation_source` **物理删除**，不留脏数据 |
| 旧版兼容 | **不做**任何旧插件 / 旧服务端兼容设计；用户会重新全量刮削 |

## 2. 服务端：演员艺名模型

### 2.1 表结构

`actor_person` 一人一行，只存艺名与身份：

| 列 | 说明 |
|---|---|
| `id` | 主键 |
| `stage_name` | 艺名（复用旧 `display_name` 列），显示 / 合集 / 搜索都用它 |
| `stage_key` | 匹配键：NFKC 全半角统一、去首尾空白、忽略大小写与所有空白 |
| `stage_source` | 新增，`''`=自动学习，`manual`=手动改过（`person-edit` 写入时置位） |
| `provider` + `actor_id` | 身份唯一索引 |
| `created_at` / `updated_at` | 时间戳 |

**迁移**（`DBAutoMigrate`，沿用已有 `DropTable("actor_name")` 先例）：

1. `AutoMigrate` 补出 `stage_source` 列；
2. `Migrator().DropColumn` 物理删除 `translated_name`、`translated_key`、`translation_source`
   三列（先 `HasColumn` 判断，幂等；SQLite 与 Postgres 均走 GORM 迁移器）；
3. `DELETE FROM translation_metadata WHERE kind='actor'`，清空演员术语译文；
4. `backfillActorPersonKeys` 只回填 `stage_key`（删除译名键回填分支）。

配套迁移回归测试（沿用 `actor_migration_test.go` 模式）：构造 v1.8.9 结构（含三列与数据）
→ 迁移 → 断言三列不存在、`stage_source` 存在、艺名数据完好、actor 术语行被清空。

### 2.2 艺名评选规则（服务端集中）

`PUT /v1/actor-aliases` 接收候选名字池 `names`，服务端从中选艺名：

- **汉字数最多者胜出**。汉字范围：CJK 统一表意文字 `U+4E00–U+9FFF`、扩展 A `U+3400–U+4DBF`、
  兼容表意文字 `U+F900–U+FAFF`；假名、罗马字、拉丁字母计 0。
- 平手取池内顺序第一个。插件按固定顺序入池（见 3.2），服务端不重排。
- 入池前按 `stage_key` 同口径去重（NFKC + 忽略大小写空白）。

覆盖策略（按 `provider + actor_id` 找到或创建身份）：

| 场景 | 行为 |
|---|---|
| 新身份 | 直接写优选名，`stage_source=''` |
| 已有身份，`stage_source=manual` | 仅 `source=person-edit` 可覆盖（覆盖后仍 `manual`） |
| 已有身份，自动 | 新名汉字数**严格更多**才升级；平手或更少保留现有 |
| `person-edit` 提交的新名恰为「X（当前艺名）」复合格式 | 视为遗留显示名，**不覆盖**（防污染护栏，全角/半角括号都识别） |

### 2.3 接口契约（私有路由，全部不保留旧字段）

- `GET /v1/actor-aliases?name=`：只按 `stage_key` 查；同名多身份返回 `ambiguous` 与 `matches`。
- `POST /v1/actor-aliases/lookup`：批量查表，契约不变（响应 person 去掉译名字段）。
- `PUT /v1/actor-aliases`：请求 `{names: [候选池], provider, actor_id, source}`，
  `source` 取 `auto`（解析器）或 `person-edit`（手动改名写回）；`names` 必填、至少一个非空。
- `POST /v1/actor-aliases/merge`：`{person_ids, stage_name}`，手工合并；给了 `stage_name`
  就置 `manual`。
- 响应 person 统一为 `{id, stage_name, provider, actor_id}`。

### 2.4 术语字典

- `TranslationKindActor` 常量与校验分支删除，`kind=actor` 请求返回 400。
- `maker` / `label` 两个 kind 维持现状（此前决定，与本次无关）。
- 系列 / 类别术语链路（首写优先、进程缓存）不变。

### 2.5 零改动部分

演员搜索（`SearchActorAll`、来源优先 MINNANO/AVBASE/Gfriends）、演员详情
（含 Gfriends 图片注入）、`/v1/translate` 引擎注册表（baidu/google/googlefree/deepl/openai）
全部不动。MINNANO 名字解析（h1 日文名 + span 英文名兜底、两词交换姓名，参考
`kanojo-db/scrapers` 的 `minnanoav.py`）保持已实施状态。

## 3. 插件：演员身份解析

### 3.1 流程

`ActorIdentityResolver.ResolveAllAsync(rawNames, cancellationToken, log)`（删除 translate 参数）：

1. `ActorNameHelper.Parse` 拆 `A（B）`：B 做搜索名，A 进候选池；无括号时整串即搜索名。
2. 整片演员名批量查表（`POST lookup`，负缓存 15 分钟机制保留）。
3. **命中唯一身份**：按表里 `provider + actor_id` 取演员详情（走 `ActorInfoCache`）
   → 组候选池 → `PUT` → 用返回的 `stage_name` 显示。
4. **未命中 / 歧义**：现有来源质量排序（MINNANO → AVBASE → AV-LEAGUE / ThePornDB →
   Gfriends → Wikipedia）+ 含汉字优先 + 名字匹配校验（最多 3 个候选）选身份
   → 取详情 → 组候选池 → `PUT` → 用返回艺名。
5. 同一部片按 pid 去重；进程内按原始名缓存解析结果。
6. 搜索不到演员：保留原始名，不猜身份、不回写。

`ResolvedActor` 精简为 `Name`（=服务端艺名）+ `RawName` + 身份（Provider/ActorId）
+ 头像来源（ImageSource/GfriendsImageSource）。删除 `DisplayName` / `SourceDisplayName`
二分、`CachedTranslatedName`、`SearchName` 显示用途。

### 3.2 候选池组成与顺序

固定顺序（平手时服务端取第一个）：

1. 详情 `Name`（选中身份的规范名）；
2. 详情 `Aliases`（按返回顺序）；
3. A（影片来源已转好的汉字名）；
4. 各搜索结果 `Name`（按来源质量排序）。

详情取不到时退化为「A + 搜索结果名」；查表命中但详情失败时直接用表里艺名、不 PUT。
**插件不做汉字评分**，只收集与排序。

### 3.3 请求量

- 详情走现有 `ActorInfoCache`（TTL 6 小时、上限 2000），与头像阶段共享：
  解析阶段先取，头像阶段命中缓存，净增请求≈0。
- 查表命中路径每个进程生命周期每位演员一次 PUT（幂等，服务端无变化时不写库）。
- 删除旧服务端降级分支（`_batchDisabled`、404 特判）；**网络级降级保留**：
  查表 / PUT 异常 → 进程内禁用演员表、只 Warn 一次，退化为「搜索 + 详情」，刮削不中断。

### 3.4 名字辅助与演员页

- `ActorNameHelper`：保留 `Parse`；删除 `FormatDisplay`、`ResolveTranslatedCollisions`
  （无译名后显示名即艺名，撞名回退失去意义；同名不同人由 Jellyfin 按名字合并的固有行为不变）。
- `ResolvePersonDisplay` 简化：已有名字优先 → 空名用表艺名 → 退回演员接口名（删除 translate 参数）。
- `ActorProvider.GetMetadata` 刷新逻辑不变（R26 语义：手动名字最高优先级）。
- `MovieProvider`：`m.Actors = resolved.Select(a => a.Name)`；头像 / pid 映射不变。

### 3.5 手动改名写回（R25/R26 新语义）

「同步演员合集」任务内的演职表对齐保留（Person.Name → People）；写回改为：

- `PUT {names: [新名字], provider, actor_id, source: "person-edit"}`，服务端标 `manual`，
  此后自动升级不碰它；
- 无 pid 时仍按旧名、新名**原样**依次反查身份（R26 口径，不解析括号）；
  遗留复合旧名查不到 `stage_key` 时记 Warn（与第 6 节边界一致）；写入失败同样记 Warn；
- 旧复合名护栏在服务端（2.2），插件不再解析括号拆译名。

## 4. 合集与字段级聚合影响

### 4.1 演员合集

机制全部不变：合集名取影片 People 显示名（现在=艺名）、R23 每日全删重建、
R24 锁、多人共演 / 无演员影片、R11 媒体库白名单、R4 空合集清理、R5 换图跟随。
重刮后 People 变成艺名，每日任务重建的合集自然换成艺名。

### 4.2 字段级聚合：不受影响

- 聚合（`AggregateMovie` / `mergeMovieInfos`）在解析器**上游**：`Actors` 字段按
  `field_priority` 链取第一个非空的**影片源原始名字列表**，不经过演员翻译、不读写
  `actor_person`。删译名不改变聚合的任何输入输出。
- `EnableRealActorNames`（AVBASE 真实名替换）也只换原始名字列表，随后照常进解析器。
- 解析器接管后，艺名由服务端汉字优选决定，**与聚合取了哪个源的名字无关**——
  不同源的名字写法差异被候选池吸收。`Actors: 源1,源2` 字段优先级配置继续有效。

## 5. 主辅翻译引擎

### 5.1 配置模型

- 删除：`TranslationEngine` 枚举与下拉、`GoogleApiKey` / `GoogleApiUrl`（谷歌付费）、
  `DeepLApiKey` / `DeepLApiUrl`、`TranslateActor` 勾选。
- 新增：`SecondaryTranslationEngine` 枚举 **None / Baidu / GoogleFree，默认 None**。
- 保留：OpenAI 三项（`OpenAiApiUrl` / `OpenAiApiKey` / `OpenAiModel`）作为主引擎固定配置，
  配置页常显；`BaiduAppId` / `BaiduAppKey` 仅在辅引擎=Baidu 时显示。
- 翻译勾选 5→4：标题 / 简介 / 系列 / 类别；目标语言仍固定 `zh-CN`；全不勾=不翻译。
- 不迁移旧配置：升级后主引擎未填 + 辅引擎 None = 翻译保留原文，填好配置即启用。

### 5.2 编排（插件 `TranslationHelper`）

每次翻译（标题/简介直译、系列/类别术语引擎调用共用）：

1. **主引擎**：`OpenAiApiKey` 非空 → 调 OpenAI（现有 1s 限速、5 次重试、模型留空自动探测）；
   成功即返回。未配置密钥视为跳过。
2. **辅引擎**：主引擎失败或跳过 → 按配置调 Baidu（1s 限速，需 App ID/Key）
   或 GoogleFree（600 字符分块、单块 20s 超时、100ms 限速）；成功即返回。
   选了 Baidu 但凭据未填 → 视为不可用，直接进入第 3 步。
3. 都不可用 / 都失败 → 抛异常：标题/简介保留原文；术语保留原文且**不缓存**（下次可重试）。
4. 取消（`OperationCanceledException`）直接向上抛，不触发回退。

`LogResolvedModelAsync` 探测条件改为「主引擎有密钥且模型留空」。
术语字典链路（进程缓存 → 服务端 GET → 引擎 → PUT 回写、首写优先）不变，
仅 `TermKind.Actor` 删除。

### 5.3 服务端与界面

- SDK `/v1/translate` 与引擎注册表零改动（百度/谷歌免费引擎已存在）。
- `configPage.html`：删除演员勾选与谷歌付费/DeepL 区块；引擎下拉换成辅引擎下拉
  （无/百度/谷歌免费）；OpenAI 区块常显。Emby 侧 `DisplayName` / `VisibleCondition` 同步。
- i18n 字典同步增删，用 `tmp/i18n_check.py` 复核文本节点全覆盖。

## 6. 边界与已知代价

- **存量 Person 不自动改名**：用户手动删旧 Person 后重刮。没删干净的旧 Person，
  每日任务仍按 Person.Name 对齐演职表（显示旧名直到删除），但服务端护栏保证
  「译名（艺名）」复合名**不会写进字典当艺名**。
- 不做旧版兼容的自然后果（非设计目标）：旧插件 PUT 带的 `translated_name` 字段被忽略、
  响应拿不到译名 → 旧插件只显示艺名；旧插件写 `kind=actor` 术语会 400 并触发其字典降级。
- 服务端必须文件 SQLite（`-dsn /data/metatube.db` + 持久化 `/data`）才能跨重启保留
  演员表与术语字典；内存库重启即丢（可重新学习）。
- 汉字优选只影响显示名；搜索仍用 B（假名写法搜索更准），pid 与头像由身份决定。
- 纯假名 / 罗马字演员（无汉字名）：候选池汉字数全 0，取详情规范名，与现状一致。
- 同名不同人（不同 pid 同艺名）在 Jellyfin 仍按名字合并，属固有行为；
  歧义查表返回 `ambiguous` 时不自动选身份。
